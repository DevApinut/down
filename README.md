# Facebook Multi Video Downloader

ส่วนขยาย Chromium แบบ Manifest V3 สำหรับดาวน์โหลดวิดีโอ Facebook ที่ผู้ใช้มีสิทธิ์เข้าถึง โดยออกแบบให้ปุ่มดาวน์โหลดผูกกับ **Video ID ของตัวเล่นที่กำลังแสดงอยู่จริง** เพื่อลดปัญหาดาวน์โหลดวิดีโอผิดโพสต์

เอกสารนี้อธิบายแนวคิดและข้อควรระวังสำหรับผู้ที่จะพัฒนาต่อ อ้างอิงโค้ดเวอร์ชัน `0.6.67`

## เป้าหมายหลักของระบบ

1. ปุ่มดาวน์โหลดต้องอยู่กับตัวเล่นวิดีโอของ Facebook และหายไปพร้อมตัวเล่นเมื่อเลื่อนฟีด
2. แหล่งดาวน์โหลดต้องตรงกับ Video ID ของตัวเล่นที่ผู้ใช้กด ห้ามเดาจากวิดีโอที่อยู่ใกล้เคียงหรือ URL ล่าสุดใน Network
3. แสดงคุณภาพเพียงหนึ่งรายการต่อความละเอียด ไม่แสดง HD/SD ซ้ำหลายลิงก์
4. รองรับทั้ง Progressive MP4 ที่มีเสียงในไฟล์ และ DASH คุณภาพสูงที่แยกภาพกับเสียง
5. ตั้งชื่อไฟล์จากคำบรรยายของโพสต์เดียวกับปุ่มที่กด และมีชื่อสำรองเมื่อหาไม่พบ
6. ห้ามรบกวนการเริ่มทำงานของ Facebook หรือทำให้หน้าค้างที่โลโก้

## พฤติกรรมที่ผู้ใช้เห็น

- เมื่อ Facebook สร้างตัวเล่น ระบบแทรกปุ่มวงกลม `⇩` เข้าไปในผลลัพธ์ React ของตัวเล่นนั้น
- ปุ่มเป็นส่วนหนึ่งของโครงสร้างตัวเล่น จึงเลื่อนและหายไปพร้อมโพสต์ ไม่ลอยค้างบนหน้าจอ
- เมื่อกดปุ่ม จะเปิดเมนูคุณภาพของ Video ID นั้นเท่านั้น
- Progressive แสดงเป็น `SD` หรือ `HD` พร้อมเสียง
- DASH แสดงตามความละเอียดจริง เช่น `720p`, `1080p`, `1440p`, `2160p` และระบบพยายามรวมเสียงให้
- รายการที่มีป้ายความละเอียดเดียวกันจะถูกรวมให้เหลือรายการที่ดีที่สุดเพียงรายการเดียว
- ชื่อไฟล์มีรูปแบบ `คำบรรยายโพสต์ [คุณภาพ].mp4`
- หากไม่มีคำบรรยาย จะใช้ `facebook-video-<video-id> [คุณภาพ].mp4`

คุณภาพที่แสดงขึ้นอยู่กับไฟล์ที่ Facebook ส่งให้สำหรับวิดีโอนั้น ส่วนขยายไม่สามารถสร้าง 1080p หรือ 4K ขึ้นมาเองได้

## ภาพรวมการไหลของข้อมูล

```text
Facebook โหลดโมดูล VideoPlayerRelay.react
              │
              ▼
page-bridge.js ดัก factory และห่อ React component
              │
              ├─ อ่าน Video ID จาก payload ของตัวเล่น
              ├─ อ่าน Progressive URL จาก payload/Relay/metadata
              ├─ อ่านและแยก DASH MPD เป็น videoTracks + audioTracks
              └─ แทรกปุ่ม ⇩ เข้าในผลลัพธ์ React ของตัวเล่นนั้น
              │
              ▼
ผู้ใช้กดปุ่ม → เลือกคุณภาพ → ส่ง Video ID + source + caption
              │
              ▼
content.js ตรวจข้อมูล ตั้งชื่อไฟล์ และส่งงาน
              │
              ▼
service-worker.js
       ├─ Progressive: ส่ง URL ให้ Chrome Downloads โดยตรง
       └─ DASH: ส่งให้ offscreen.js รวมภาพกับเสียง หากรวมไม่ได้ให้โหลดแยก
```

## เหตุผลที่ใช้ VideoPlayerRelay.react

Facebook เป็น Single Page Application และนำ DOM กลับมาใช้ซ้ำเมื่อเลื่อนฟีด การจับคู่ด้วยวิธีต่อไปนี้มีโอกาสเลือกวิดีโอผิด:

- เลือก `<video>` ที่อยู่ใกล้ปุ่มที่สุด
- ใช้ URL วิดีโอล่าสุดที่เห็นใน Network
- ใช้ลำดับโพสต์หรือลำดับ `<video>` บนหน้า
- หน่วงเวลา 1–2 วินาทีแล้วเดาว่าแหล่งล่าสุดเป็นของตัวเล่นนั้น

แนวทางปัจจุบันอ่าน `payload.video.__id`, `payload.video.id`, `videoId` หรือ `video_id` ตอน React เรียก component ของตัวเล่น แล้วบันทึกแหล่งต่าง ๆ ภายใต้ ID เดียวกัน ปุ่มที่สร้างขึ้นจะเก็บ ID นี้ไว้ใน closure จึงไม่ต้องเดาว่าผู้ใช้กดวิดีโอใด

หลักสำคัญสำหรับคนทำต่อ: **อย่าเปลี่ยนกลับไปจับคู่ด้วยตำแหน่ง DOM หรือเวลาที่ request เกิด** หากมีข้อมูลไม่พอ ควรแสดงว่าไม่พบแหล่งแทนการเสี่ยงโหลดผิดวิดีโอ

## การค้นหาแหล่งวิดีโอ

`page-bridge.js` รักษา catalog แยกตาม Video ID โดยมีข้อมูลสามกลุ่ม:

- `progressive` — MP4 ที่มีภาพและเสียงใน URL เดียว มักระบุเป็น SD/HD
- `videoTracks` — ภาพจาก DASH อาจมี 720p, 1080p, 1440p หรือ 2160p
- `audioTracks` — เสียงจาก DASH สำหรับนำไปรวมกับ video track

แหล่งข้อมูลที่รองรับประกอบด้วย:

- ฟิลด์ใน payload ของ `VideoPlayerRelay.react`
- `playable_url` และ `playable_url` ที่ร้องขอด้วย `{quality: "HD"}`
- `video_delivery_response.progressive_urls`
- `playlist` แบบ `MPEG_DASH`
- `manifest_xml` หรือ DASH manifest ที่ฝังใน metadata
- ข้อมูล Network ที่ service worker เห็น ใช้เป็นแหล่งเสริม ไม่ใช่ตัวตัดสินการจับคู่เพียงอย่างเดียว

ก่อนบันทึก URL ระบบลบช่วง `bytestart`/`byteend` เพื่อใช้ URL หลักเป็นกุญแจลดรายการซ้ำ

## การรวมรายการคุณภาพซ้ำ

Facebook อาจส่ง URL หลายตัวสำหรับคุณภาพเดียวกันจาก payload, Relay และ delivery response จึงห้ามสร้างหนึ่งเมนูต่อหนึ่ง URL โดยตรง

`availableQualitySources(videoId)` ทำงานดังนี้:

1. Progressive จัดกลุ่มด้วยป้ายความละเอียด เช่น `direct:HD` และ `direct:SD`
2. หากกลุ่มเดียวกันมีหลาย URL ให้เก็บตัวที่ bitrate สูงกว่า
3. DASH จัดกลุ่มด้วยความสูงจริง เช่น `dash:1080P`
4. หากความละเอียดเดียวกันมีหลาย encoding ให้เก็บตัวที่ bitrate สูงกว่า
5. เรียงความละเอียดจากสูงไปต่ำ

หากเพิ่ม codec หรือรูปแบบใหม่ ควรคงหลัก “หนึ่งตัวเลือกต่อความละเอียด” และเลือกตัวที่เล่นได้แน่นอนที่สุดก่อน bitrate

## Progressive และ DASH

### Progressive

- มีภาพและเสียงในไฟล์เดียว
- ดาวน์โหลดตรงผ่าน `chrome.downloads`
- เริ่มเร็วและใช้หน่วยความจำน้อย
- โดยทั่วไป Facebook ให้เพียง SD หรือ HD

### DASH

- Facebook แยกไฟล์ภาพและเสียง
- ความละเอียดสูงกว่า เช่น 1080p หรือ 4K มักอยู่ในรูปแบบนี้
- ระบบเลือก audio track ที่ bitrate สูงสุดมาคู่กับ video track
- `offscreen.js` ใช้ FFmpeg/WASM รวมเป็น MP4 ไฟล์เดียว
- จำกัดขนาดงานรวมในเบราว์เซอร์ไว้ที่ 4 GiB (`MAX_BROWSER_MERGE_BYTES`)
- หากรวมไม่สำเร็จ ระบบ fallback เป็น `[video].mp4` และ `[audio].m4a` เพื่อไม่ให้งานสูญหาย

การเพิ่มคุณภาพสูงต้องอ่าน DASH manifest ไม่ใช่การปรับ URL ของ HD หรือขยายภาพเทียม

## การตั้งชื่อไฟล์จากโพสต์

เมื่อผู้ใช้กดปุ่ม `postCaptionFromTrigger()` จะหา root ของปุ่มจาก:

```text
[role="article"], article, [role="dialog"]
```

จากนั้นให้ความสำคัญกับ selector ของข้อความโพสต์:

```text
[data-ad-preview="message"]
[data-ad-comet-preview="message"]
[data-testid="post_message"]
[data-ad-rendering-role="story_message"]
```

หากไม่พบจึงพิจารณา `[dir="auto"]` ภายใน root เดียวกัน ห้ามค้นหาคำบรรยายที่ยาวที่สุดจากทั้งหน้า เพราะอาจหยิบชื่อจากโพสต์อื่น

`content.js` ทำความสะอาดอักขระที่ Windows ไม่อนุญาต (`<>:"/\\|?*` และ control characters), ลดช่องว่าง, จำกัดชื่อไฟล์ 150 ตัวอักษร และต่อท้ายคุณภาพ

## หน้าที่ของแต่ละไฟล์

- `manifest.json` — สิทธิ์, content script, CSP และหมายเลขเวอร์ชัน
- `page-bridge.js` — ทำงานใน MAIN world, ดักโมดูล Facebook, ผูก Video ID, สร้างปุ่ม/เมนู และอ่าน metadata
- `content.js` — ทำงานใน isolated world, รับข้อความจาก page bridge, ตั้งชื่อไฟล์, UI ดาวน์โหลดหลายรายการ และส่งงานให้ service worker
- `styles.css` — รูปแบบ UI ฝั่ง content script
- `service-worker.js` — ลงทะเบียน `page-bridge.js` แบบ `document_start`, เก็บ Network source, จัดคิวและติดตาม Chrome Downloads
- `offscreen.html` / `offscreen.js` — สภาพแวดล้อมสำหรับรวม DASH ภาพ+เสียงด้วย FFmpeg/WASM
- `vendor/ffmpeg` และ `vendor/core` — runtime สำหรับงานรวมไฟล์
- `react-bridge.js` และ `vendor/esuit-relay-proxy.js` — ไฟล์ทดลอง/อ้างอิงจากแนวทางก่อนหน้า ปัจจุบัน **ไม่ถูกลงทะเบียนและห้ามเปิดใช้โดยไม่ทดสอบใหม่**

ชื่อวิดีโอทุกเส้นทางต้องลงท้าย `.mp4` แม้เข้าสู่ fallback โดย `content.js` ต้องส่งชื่อเต็ม และ `service-worker.js` ใช้ `ensureFilenameExtension()` เป็นด่านสุดท้ายก่อนเรียก Chrome Downloads ส่วนไฟล์ทั่วไปของกลุ่มต้องไม่ถูกบังคับเป็น MP4

## ข้อควรระวังสำคัญ

### ห้ามเปิด bridge เก่าพร้อมกัน

รุ่นก่อนเคยลงทะเบียน MAIN-world script หลายตัว (`proxy`, `react bridge` และ page bridge) พร้อมกัน ทำให้แก้ factory/React ซ้ำและ Facebook ค้างที่หน้าโลโก้ ปัจจุบัน `service-worker.js` ถอนทะเบียน script เก่าและลงทะเบียนเฉพาะ `page-bridge.js`

อย่าเพิ่ม `react-bridge.js` หรือ `vendor/esuit-relay-proxy.js` กลับเข้า registration เพียงเพราะไฟล์ยังอยู่ในโครงการ หากต้องทดลองควรทำใน branch แยกและตรวจหน้า login, feed, watch, reels และ dialog ก่อน

### ห้ามใช้ inline script injection

Facebook ใช้ Content Security Policy ที่บล็อก inline script ซึ่งเคยทำให้พบข้อความ `Executing inline script violates Content Security Policy` การทำงานใน MAIN world ให้ใช้ `chrome.scripting.registerContentScripts({world: "MAIN"})` แทน การใส่ `<script>...</script>` โดยไม่มี nonce จะถูกบล็อก

### อย่ารอเวลาแบบตายตัว

ระบบไม่ควรบังคับรอ 1–2 วินาที เพราะความเร็วของ Relay/Network ต่างกันในแต่ละเครื่อง ใช้ event, module hook, catalog update และ Video ID เป็นหลัก หากข้อมูล DASH มาทีหลัง เมนูครั้งถัดไปควรอ่าน catalog ล่าสุด

หากกดปุ่มตอน catalog ยังไม่มี source ห้ามเข้า fallback แล้วดาวน์โหลดทันที ให้เปิดเมนูแจ้งว่ากำลังค้นหาคุณภาพแทน เพื่อให้ผู้ใช้เป็นคนเลือกทุกครั้ง

### Reels ต้อง fail-safe

ต้องเรียก component เดิมของ Facebook ให้เสร็จก่อนอ่าน payload เสมอ และครอบการอ่าน metadata ด้วย `try/catch` เพื่อไม่ให้ข้อผิดพลาดของส่วนขยายทำลายตัวเล่น หน้า `/reel` และ `/reels` ใช้ปุ่ม exact แบบเดียวกับฟีด โดยการแทรกปุ่มจะเกิดหลัง component เดิมคืนผลลัพธ์แล้วเท่านั้น วิธีนี้ทำให้ปุ่มถือ Video ID ที่ถูกต้องและไม่ต้องพยายามแกะ URL จาก `<video src="blob:...">`

ห้ามข้ามการติดตั้ง wrapper ทั้งโมดูลเพียงเพราะเริ่มต้นอยู่หน้า Reels เพราะ Facebook cache โมดูลไว้ เมื่อออกจาก Reels โดยไม่รีเฟรช โมดูลจะไม่ถูกโหลดใหม่และปุ่มในหน้าปกติจะหายตลอด session นั้น

สาเหตุสำคัญของหน้า Reels พังในรุ่นก่อนคือเรียก `capturePlayerVideoId()` ก่อน `Reflect.apply()` ของ component เดิม การเดิน payload อาจแตะ Relay proxy/getter และโยนข้อผิดพลาดก่อน Facebook render ตัวเล่น ลำดับที่ถูกต้องคือ render เดิมก่อน จากนั้นจึง capture แบบ fail-safe

Facebook อาจเก็บหน้าก่อนหน้าและ `.fbmd-react-download` ไว้ใน DOM แบบซ่อนหลังเปิด/ปิด Reels ห้ามใช้เพียง `document.querySelectorAll(...).length` ตัดสินว่าจะซ่อน overlay เพราะปุ่มที่ค้างอยู่อาจไม่ใช่ของวิดีโอที่มองเห็น ต้องตรวจขนาด, viewport, `display` และ `visibility` ของปุ่มก่อน หากไม่มีปุ่ม exact ที่มองเห็น ให้เปิดระบบ overlay สำหรับ `<video>` ปัจจุบัน

### อย่าดาวน์โหลด URL ที่หมดอายุ

ลิงก์ CDN ของ Facebook มีอายุจำกัด หาก Chrome ตอบว่าลิงก์ใช้ไม่ได้ ให้ผู้ใช้รีเฟรชหน้า เล่น/เปิดวิดีโออีกครั้ง และเลือกดาวน์โหลดใหม่ ไม่ควรเก็บ URL ข้าม session เป็นเวลานาน

## การติดตั้งสำหรับทดสอบ

1. เปิด `chrome://extensions` หรือ `edge://extensions`
2. เปิด Developer mode
3. กด Load unpacked
4. เลือกโฟลเดอร์โครงการนี้
5. หลังแก้โค้ด ให้กด Reload ที่การ์ดส่วนขยาย
6. รีเฟรช Facebook หนึ่งครั้ง เพราะ MAIN-world hook ต้องเริ่มที่ `document_start`

## รายการทดสอบก่อนส่งรุ่นใหม่

- Facebook เปิดผ่านหน้าโลโก้ได้ ไม่ค้าง และ login ได้
- ฟีดหลัก, Watch, Reels, permalink และวิดีโอใน dialog ยังทำงาน
- ปุ่ม `⇩` อยู่กับวิดีโอ และหายไปเมื่อโพสต์ถูกเลื่อนออก/ถอดจาก DOM
- กดวิดีโอหลายโพสต์สลับกันแล้ว URL/ชื่อไฟล์ตรงกับโพสต์ที่กดทุกครั้ง
- HD และ SD ไม่ปรากฏซ้ำ
- หากมี DASH เมนูแสดง 720p/1080p/1440p/2160p ตาม manifest จริง
- Progressive ได้ไฟล์เดียวพร้อมเสียง
- DASH ขนาดที่รองรับรวมเป็นไฟล์เดียวและเล่นได้ทั้งภาพ/เสียง
- เมื่อรวม DASH ไม่ได้ fallback สองไฟล์ทำงาน
- ชื่อไทย, emoji, ขึ้นบรรทัดใหม่ และอักขระต้องห้ามไม่ทำให้ดาวน์โหลดล้มเหลว
- เลื่อนฟีดเร็ว ๆ แล้วไม่มีปุ่มลอยผิดตำแหน่งหรือชื่อข้ามโพสต์
- `node --check page-bridge.js`, `content.js`, `service-worker.js` และ `offscreen.js` ผ่าน

## Diagnostics

ข้อความลักษณะ `P2 R0 C7 I0 S0` ใช้ดูว่าขั้นตอนไหนมีข้อมูล:

- `P` — จำนวน player/video IDs ที่ hook พบ
- `R` — จำนวนแหล่ง Relay ที่จับได้
- `C` — จำนวนรายการใน catalog
- `I` — จำนวน video element ที่ผูก ID จาก React fiber ได้
- `S` — สถานะ direct Relay store capture

ตัวอย่าง `P2 R0 C7 I0 S0` หมายถึง hook ตัวเล่นทำงานและ catalog มีข้อมูล แม้ยังจับ Relay store โดยตรงไม่ได้ ดังนั้นหาก progressive URL มาจาก payload แล้ว ปุ่มเฉพาะตัวเล่นยังสามารถดาวน์โหลดได้ ไม่ควรบังคับให้ `R` หรือ `I` ต้องมากกว่าศูนย์เสมอ

## แนวทางเพิ่มความสามารถในอนาคต

- แสดง codec, bitrate, FPS และขนาดโดยประมาณในเมนู โดยยังจัดกลุ่มหลักตามความละเอียด
- เลือก codec ที่เบราว์เซอร์/ตัวรวมรองรับดีที่สุดเมื่อความละเอียดเท่ากัน
- ทำระบบรวมไฟล์ขนาดใหญ่นอกหน่วยความจำ หากต้องรองรับงานเกินข้อจำกัด WASM
- เพิ่ม automated fixture สำหรับ Relay payload และ DASH MPD เพื่อทดสอบ parser โดยไม่ต้องพึ่งหน้า Facebook จริง
- เพิ่ม telemetry เฉพาะในเครื่องสำหรับเหตุผลที่ source ถูกตัดออก โดยห้ามส่ง URL หรือข้อมูลโพสต์ออกภายนอก

## การออกรุ่น

เมื่อเปลี่ยนพฤติกรรมส่วนขยาย:

1. เพิ่ม `version` ใน `manifest.json`
2. ตรวจ syntax ของ JavaScript ทุกไฟล์ที่แก้
3. กด Reload ส่วนขยายและรีเฟรช Facebook
4. ทดสอบตามรายการด้านบน โดยเฉพาะการจับคู่หลายโพสต์และหน้าโลโก้
5. อัปเดต README หากโครงสร้างหรือ fallback เปลี่ยน
